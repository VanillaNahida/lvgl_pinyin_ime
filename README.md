**English** | [简体中文](README_zh-cn.md)

`lvgl_pinyin_ime` is an LVGL widget that any ESP-IDF project can pull in as a
component: hand it a `lv_textarea` and it owns the keyboard, the candidates, the
commit target and pinyin decoding.

- Engine: [libgooglepinyin](https://salsa.debian.org/input-method-team/libgooglepinyin) (vendored, Apache-2.0)
- Keyboards: 26-key full keyboard + 9-key (T9), plus a shared digit / symbol panel set
- Input: full pinyin, phrases, whole sentences, candidate paging, syllable separator `'`, Chinese/English toggle
- Dictionary: flash partition / SD card / embedded, with an automatic fallback to the embedded copy when the `dict` partition is missing
- Fonts: embedded as C arrays by default (nothing to flash); a `font` partition is optional
- Voice input (optional): iFlytek streaming dictation - the component runs the protocol, your application supplies the socket and the microphone
- Targets: ESP32-S3 (primary), ESP32-P4; ESP32-S31 is a preview target
- Reference board: ST7789 (SPI, 320 x 240 landscape) + XPT2046 touch

**Not sure where to start?** To just build, flash and see it run, jump to
[Quick start](#quick-start-run-the-example). To wire it into your own project,
see [Use it in your own project](#use-it-in-your-own-project).

## Quick start (run the example)

Four steps: prepare the environment, generate the dictionary and fonts, build,
flash.

### 0. Prerequisites

| What | Notes |
| --- | --- |
| ESP-IDF 6.1 | exported into the current PowerShell session |
| Python 3.8+ | generates the dictionary and fonts; always inside `tools/venv`, never globally |
| Node.js LTS | only needed to generate fonts (`lv_font_conv` dependency), `winget install OpenJS.NodeJS.LTS` |

### 1. Export the IDF environment

`idf.py` and `esptool` are injected into the session by this script, so run it
once per new terminal:

```powershell
& "D:\Espressif\EIM\v6.1\esp-idf\export.ps1"   # replace with your IDF path
```

### 2. Generate the dictionary and fonts (required on first checkout)

Generated files are **not committed** (only the source word lists under `data/`
are), so a fresh checkout must generate them first - otherwise the build stops
with a clear error about the missing `generated/lv_font_ime_*.c`.

```powershell
# create the isolated venv and install dependencies (once)
powershell -ExecutionPolicy Bypass -File tools\setup_env.ps1

# charset -> font C arrays; word list -> dictionary
.\tools\venv\Scripts\python.exe tools\gen_charset.py
.\tools\venv\Scripts\python.exe tools\gen_font.py
python tools\gen_dict.py
```

### 3. Build

**The repository root is a component, not a project** - `idf.py` has to run from
a project directory, otherwise CMake tries to configure the repo root as a
project and fails with host compiler errors. The example project lives in
`examples/k26_k9_demo`:

```powershell
cd examples\k26_k9_demo
idf.py set-target esp32s3        # once; change it when you switch chips
idf.py build
```

The first build downloads LVGL 9.5 into `managed_components/`.

### 4. Flash and watch the log

```powershell
idf.py -p COM5 flash monitor     # COM5 is your serial port; Ctrl + ] quits
```

`idf.py flash` writes the bootloader, the partition table and the application.
The application carries a fallback copy of the dictionary, so it **works without
flashing the `dict` partition**.

The demo prints a widget dump at start-up (`lv_pinyin_ime_dump`) and an error if
the engine or the fonts are missing, so the monitor output answers "why is the
keyboard not there". Wiring, touch calibration and display troubleshooting are
in [docs/usage.md](docs/usage.md).

## Use it in your own project

### 1. Declare the dependency

The component is pulled in through the ESP-IDF component manager.
`main/idf_component.yml`:

```yaml
dependencies:
  idf: ">=5.3"
  lvgl/lvgl: "^9.5"
  lvgl_pinyin_ime:
    version: "*"          # once published to the component registry
    # or, during development, override with a local path:
    # override_path: "../../lvgl_pinyin_ime"
```

### 2. Make main depend on it

`main/CMakeLists.txt`:

```cmake
idf_component_register(
    SRCS "main.c"
    INCLUDE_DIRS "."
    REQUIRES lvgl lvgl_pinyin_ime
)
```

### 3. Write the code

```c
#include "lvgl_pinyin_ime/lv_pinyin_ime.h"

lv_obj_t *ta  = lv_textarea_create(lv_screen_active());
lv_obj_t *ime = lv_pinyin_ime_create(lv_screen_active());

lv_pinyin_ime_attach(ime, ta);                        /* commit target */
lv_pinyin_ime_set_mode(ime, LV_PINYIN_IME_MODE_K26);  /* 26-key / 9-key */
lv_pinyin_ime_set_lang(ime, LV_PINYIN_IME_LANG_CN);   /* Chinese / English */

/* Sent when ✓ is pressed with an empty pinyin buffer: hide the keyboard */
lv_obj_add_event_cb(ime, on_ime_ready, lv_pinyin_ime_event_ready(), NULL);
```

The callback:

```c
static void on_ime_ready(lv_event_t *e)
{
    lv_obj_add_flag(ime, LV_OBJ_FLAG_HIDDEN);   /* hide the keyboard */
}
```

That is all you need. The three calls below are global state read when a widget
is built, so call them **before** `lv_pinyin_ime_create()`; changing them later
does not re-lay out an existing widget:

- `lv_pinyin_ime_set_fit_height(px)` - derive the row height from a target
  widget height; the simplest way to make the keyboard fill half the screen
- `lv_pinyin_ime_set_row_height(px)` - when you want a fixed row height
- `lv_pinyin_ime_set_fonts(big, small)` - use the application's own CJK font,
  which usually covers more characters and avoids missing-glyph boxes

Partition tables, dictionary sources, the two font modes and the SD extended
dictionary are covered in [docs/integration.md](docs/integration.md); the full
API is under [include/lvgl_pinyin_ime/](include/lvgl_pinyin_ime/).

## Voice input (optional)

A voice key on the keyboard drives a streaming speech-to-text session against the
[iFlytek dictation WebAPI](https://www.xfyun.cn/doc/asr/voicedictation/API.html).
Enable it with `CONFIG_LV_PINYIN_IME_VOICE_ENABLE` and fill in the credentials
under `LVGL Pinyin IME → Voice input` in menuconfig.

The component deliberately opens **no socket and no I2S**: the application
provides four callbacks (`ws_open` / `ws_send_text` / `ws_close` / `audio_read`),
so the component's dependency list stays at `lvgl` + `libgooglepinyin` no matter
which cloud service, WebSocket library or audio codec you use. What the component
owns is the protocol - HMAC-SHA256 request signing, the 40 ms / 1280 byte audio
framing, reply parsing, dynamic-correction reassembly and the session state
machine.

That split is also what makes the protocol testable on a PC: the whole signing /
framing / parsing chain is verified against the samples printed in iFlytek's own
documentation, with no network and no hardware involved. The integration guide
is [docs/voice.md](docs/voice.md).

## Capabilities and status

| Capability | State |
| --- | --- |
| 26-key, 9-key (T9), digit / symbol panels (P1/P2/P3) | available |
| Full pinyin, phrases, whole sentences; candidate paging; separator `'`; Chinese/English toggle | available |
| Dictionary from partition / SD / embedded, with partition fallback | available |
| Fonts embedded (default) or on a `font` partition | available |
| Voice input (iFlytek streaming dictation) | available (off by default; bring your own Wi-Fi and microphone) |
| Double pinyin, fuzzy pinyin, association, user frequency learning, SD extended dictionary | planned, not landed |

> The "planned" items already have `Kconfig` entries and UI affordances (the
> separator key, for instance), but the underlying modules do not exist yet:
> there is no double-pinyin mapping, no fuzzy variants, no association (bigram)
> layer and no user dictionary persistence. The engine facade already wraps
> upstream's `im_get_predicts()` as `ime_engine_predict()`, but nothing calls it.

## Algorithm

The decoding stack has two layers; here is how much of it is actually in place.

**Engine layer (libgooglepinyin, unigram).** `im_search()` hands the spelling
string to `MatrixSearch`, which walks the syllable trie (`spellingtrie.cpp`),
looks candidates up in the lemma cache (`lpicache.cpp`) and scores them with
`NGram::get_uni_psb()`. That is a **unigram** model: each lemma carries an
independent frequency, with no cross-word context. `ngram.h` exposes only
`get_uni_psb()` and `build_unigram()` - there is no bigram builder upstream, so
within one search step word *n* does not affect the score of word *n+1*. Word
segmentation across a multi-syllable sentence is resolved by dynamic programming
(`extend_mtrx_nd()`) over those unigram scores.

**Association layer (this project, bigram) is not landed.** The plan is that
after a candidate is committed an association layer predicts the next word; that
is where the 2-gram information would live, alongside a bigram hash table
(`ime_hash.c` - the module itself exists, but nothing calls it yet). Upstream's
association API `im_get_predicts()` is already wrapped as `ime_engine_predict()`,
but the UI does not call it. So **the only layer in effect today is the unigram
engine.**

A precise comparison with libpinyin or sunpinyin should therefore say
"libgooglepinyin's engine uses unigram scoring", not "this project uses unigram".

The 9-key path adds no scoring of its own: `ime_trie.c` maps digit strings to
candidate syllables and `ime_t9.c` expands them, both by table lookup, and the
resulting full-pinyin string is then passed to the same engine. Ranking stays in
one place - the engine.

## Related projects

If you are interested in more feature-complete pinyin input methods, try
**libpinyin** or **sunpinyin**; both are supported by fcitx and ibus. They use
more advanced algorithms (2-gram language models) and support more features, such
as double pinyin, zhuyin and fuzzy pinyin. Note that they target desktop
environments - they depend on GLib and, for sunpinyin, an SQLite-backed language
model, so they are a poor fit for an ESP32 target.

If you are looking for extra features on top of libgooglepinyin, try
**fcitx-googlepinyin**, which gives you fcitx's quick phrases, virtual keyboard,
cloud pinyin and customisable punctuation for free.
